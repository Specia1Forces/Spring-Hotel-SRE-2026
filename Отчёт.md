# Отчёт о развёртывании Spring Hotel в Minikube

## 1. Назначение приложения

Spring Hotel — клиент-серверное веб-приложение для управления гостиницей. Система предоставляет интерфейс для работы с клиентами, бронированиями, договорами, счетами, дополнительными услугами и персоналом гостиницы. Доступ к функциям разделён между сотрудниками с помощью Spring Security.

Приложение поддерживает CRUD-операции: создание, просмотр, изменение и удаление записей. Пользователь работает через веб-интерфейс, а данные сохраняются в PostgreSQL.

## 2. Состав приложения

В состав приложения входят:

- frontend — Vue 3, Vite и Nginx;
- backend — Java 25, Spring Boot 4.1.1, Spring Web MVC, Spring Data JPA и Spring Security;
- база данных — PostgreSQL 17;
- управление схемой базы данных — Liquibase;
- контейнеризация — Docker;
- оркестрация — Kubernetes в однодовой локальной инсталляции Minikube.

Frontend взаимодействует с backend по HTTP/REST. Backend работает с PostgreSQL через JDBC и Hibernate.

## 3. Docker-образы

Для приложения подготовлены два Dockerfile:

| Компонент | Dockerfile | Собранный образ |
|---|---|---|
| Backend | `Dockerfile` | `hotel-backend:0.1.0` |
| Frontend | `frontend/Dockerfile` | `hotel-frontend:0.1.0` |

Backend собирается в два этапа. В образе `eclipse-temurin:25-jdk-alpine` Maven Wrapper создаёт JAR-файл. Затем JAR переносится в облегчённый `eclipse-temurin:25-jre-alpine`. Приложение запускается не от root, а от пользователя с UID/GID `10001`, и принимает запросы на порту `8080`.

Frontend также использует multi-stage-сборку. В `node:24.15.0-alpine` выполняются `npm ci` и `npm run build`. Результат переносится в `nginx:1.28.0-alpine`. Nginx раздаёт Vue-приложение и перенаправляет запросы `/api/` во внутренний Service backend.

Для сборки использовался Docker-демон Minikube:

```powershell
& minikube -p minikube docker-env --shell powershell | Invoke-Expression

docker build -t hotel-backend:0.1.0 .
docker build -t hotel-frontend:0.1.0 .\frontend
```

Проверка и загрузка образов:

```powershell
minikube image ls | Select-String "hotel-"
minikube image load hotel-backend:0.1.0
minikube image load hotel-frontend:0.1.0
```

При сборке через `docker-env` образы сразу создаются внутри Minikube, поэтому дополнительная загрузка подтверждает наличие образов в кластере.

## 4. Использованные абстракции Kubernetes

### Namespace

Namespace `hotel` объединяет ресурсы приложения и отделяет их от системных объектов Kubernetes.

Манифест: `k8s/00-namespace.yaml`.

### ConfigMap

ConfigMap `hotel-config` хранит нечувствительную конфигурацию: JDBC URL, имя базы данных, порты, адрес backend для Nginx, разрешённый origin frontend, параметры сессии и корректного завершения.

Манифест: `k8s/01-configmap.yaml`.

### Secret

Secret `hotel-secret` хранит имя пользователя и пароль PostgreSQL. Значения передаются контейнерам через переменные окружения. В production такой Secret следует создавать отдельно от репозитория или получать из внешнего хранилища секретов.

Манифест: `k8s/02-secret.yaml`.

### PersistentVolumeClaim

PVC `postgres-data` запрашивает `1Gi` постоянного хранилища в режиме `ReadWriteOnce`. Данные PostgreSQL сохраняются при пересоздании Pod.

Манифест: `k8s/03-postgres-pvc.yaml`.

### Service

Используются три Service:

- `postgres` — headless Service для стабильного DNS-имени PostgreSQL и порта `5432`;
- `hotel-backend` — ClusterIP Service для доступа к Spring Boot по порту `8080`;
- `hotel-frontend` — ClusterIP Service, перенаправляющий порт `80` на порт контейнера `8080`.

Service выбирают Pod по labels и предоставляют постоянные сетевые имена, не зависящие от IP отдельных Pod.

Манифесты: `k8s/04-postgres-service.yaml`, `k8s/07-backend-service.yaml`, `k8s/09-frontend-service.yaml`.

### StatefulSet

StatefulSet `postgres` запускает одну реплику PostgreSQL 17. StatefulSet выбран из-за необходимости стабильного имени Pod и постоянного хранилища. Готовность PostgreSQL проверяется командой `pg_isready`.

Манифест: `k8s/05-postgres-statefulset.yaml`.

### Job

Job `hotel-migrate` однократно выполняет миграции Liquibase. Он использует тот же backend-образ, зависимости и параметры подключения, что и приложение, но запускается с профилем `admin-migrate`.

После успешной миграции Job завершается со статусом `Completed`. В обычном backend Deployment Liquibase отключён, поэтому несколько реплик backend не пытаются одновременно изменять схему.

Манифест: `k8s/06-liquibase-job.yaml`.

### Deployment

Deployment `hotel-backend` управляет Pod Spring Boot, а Deployment `hotel-frontend` — Pod Nginx/Vue. Deployment позволяют пересоздавать Pod, обновлять приложение и выполнять горизонтальное масштабирование.

Для контейнеров настроены startup, readiness и liveness probes, requests и limits ресурсов. Backend запускается с `runAsNonRoot: true`, UID/GID `10001` и seccomp-профилем `RuntimeDefault`.

Манифесты: `k8s/08-backend-deployment.yaml`, `k8s/10-frontend-deployment.yaml`.

## 5. Взаимодействие сервисов

Основной маршрут пользовательского запроса:

```text
Браузер
  → port-forward localhost:5173
  → Service hotel-frontend:80
  → frontend Pod, Nginx:8080
  → Service hotel-backend:8080
  → backend Pod, Spring Boot:8080
  → Service postgres:5432
  → Pod postgres-0
  → PVC postgres-data
```

Nginx раздаёт статические файлы Vue. Запросы `/api/` перенаправляются на `http://hotel-backend:8080`. Backend обрабатывает REST-запросы, выполняет авторизацию через Spring Security и обращается к PostgreSQL. Frontend не подключается к базе данных напрямую.

Перед запуском backend выполняется отдельная административная задача:

```text
Job hotel-migrate
  → Service postgres:5432
  → PostgreSQL
  → применение Liquibase changelog
  → Completed
```

## 6. Порядок запуска

### Minikube и образы

```powershell
minikube start --driver=docker --container-runtime=docker --cpus=4 --memory=6144
minikube status
kubectl get nodes

& minikube -p minikube docker-env --shell powershell | Invoke-Expression
docker build -t hotel-backend:0.1.0 .
docker build -t hotel-frontend:0.1.0 .\frontend
```

### PostgreSQL

```powershell
kubectl apply -f .\k8s\00-namespace.yaml
kubectl apply -f .\k8s\01-configmap.yaml
kubectl apply -f .\k8s\02-secret.yaml
kubectl apply -f .\k8s\03-postgres-pvc.yaml
kubectl apply -f .\k8s\04-postgres-service.yaml
kubectl apply -f .\k8s\05-postgres-statefulset.yaml
kubectl wait --for=condition=ready pod/postgres-0 -n hotel --timeout=180s
```

### Liquibase

```powershell
kubectl delete job hotel-migrate -n hotel --ignore-not-found
kubectl apply -f .\k8s\06-liquibase-job.yaml
kubectl wait --for=condition=complete job/hotel-migrate -n hotel --timeout=300s
kubectl logs job/hotel-migrate -n hotel
```

Статус `Completed` у Pod миграции является нормальным: одноразовая задача выполнена успешно.

### Backend и frontend

```powershell
kubectl apply -f .\k8s\07-backend-service.yaml
kubectl apply -f .\k8s\08-backend-deployment.yaml
kubectl apply -f .\k8s\09-frontend-service.yaml
kubectl apply -f .\k8s\10-frontend-deployment.yaml

kubectl rollout status deployment/hotel-backend -n hotel --timeout=180s
kubectl rollout status deployment/hotel-frontend -n hotel --timeout=180s
kubectl get pods,svc,deploy,statefulset,job,pvc -n hotel
```

В рабочем состоянии PostgreSQL, backend и frontend имеют статус `Running`, Job миграции — `Completed`, а PVC — `Bound`.

## 7. Доступ к UI и проверка CRUD

Для доступа к frontend используется port-forward:

```powershell
kubectl port-forward -n hotel service/hotel-frontend 5173:80
```

Интерфейс становится доступен по адресу `http://localhost:5173`.

Через UI проверяются авторизация и CRUD-операции: создание, просмотр, изменение и удаление записей. После обновления страницы данные сохраняются в PostgreSQL.

## 8. Масштабирование

Backend масштабируется до трёх реплик, frontend — до двух:

```powershell
kubectl scale deployment hotel-backend --replicas=3 -n hotel
kubectl scale deployment hotel-frontend --replicas=2 -n hotel
kubectl get deployments -n hotel
kubectl get pods -n hotel -o wide
```

Ожидаемое состояние Deployment:

```text
hotel-backend    3/3
hotel-frontend   2/2
```

PostgreSQL остаётся в одной реплике, поскольку в учебном задании используется одиночный экземпляр базы данных и PVC с режимом `ReadWriteOnce`.

## 9. Результат

Приложение контейнеризировано и развёрнуто в однодовом кластере Minikube. Kubernetes управляет frontend, backend, PostgreSQL и административной миграцией Liquibase. Компоненты взаимодействуют через внутренние Service, данные PostgreSQL сохраняются в PVC, а stateless-компоненты горизонтально масштабируются.

В скринкасте демонстрируются:

1. применение манифестов командой `kubectl apply`;
2. вывод Pod командой `kubectl get pods -n hotel`;
3. завершение Liquibase Job;
4. открытие UI через port-forward;
5. несколько действий в интерфейсе;
6. масштабирование backend до трёх и frontend до двух реплик;
7. повторный вывод Pod и Deployment после масштабирования.
